# superseded-practice-obsolescence-route checklist

Use this checklist before sending an adopted or shadowed practice toward
obsolescence, supersession, merge, reanchor, defer, drop, or deprecation review.

- [ ] One adopted or shadowed practice is named.
- [ ] The current stage or status is visible.
- [ ] The owner receipt target is named.
- [ ] The reason the practice should not remain active as-is is explicit.
- [ ] The route label is one of `supersede`, `merge`, `reanchor`, `defer`, `drop`, or `deprecation_review`.
- [ ] Replacement, merge target, reanchor target, defer condition, drop reason, or explicit absence of target is stated.
- [ ] Source evidence and provenance remain reachable.
- [ ] Rollback, quarantine, or restoration path is concrete enough to use.
- [ ] The smallest retained lesson is recorded.
- [ ] Memory, stats, proof, skill, routing, or runtime consequences are only downstream hints.
- [ ] The packet does not delete, deprecate, erase evidence, prove failure, write memory truth, activate a skill, change routing, or mutate runtime behavior.
